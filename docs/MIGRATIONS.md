# Database migrations (Alembic via Flask-Migrate)

The schema is managed by Alembic. `db.create_all()` is gone from production
paths (tests still use it against in-memory SQLite).

## Everyday commands

```bash
# apply pending migrations (also what Render runs on every deploy)
flask db upgrade

# after changing models.py: generate a new migration, review it, commit it
flask db migrate -m "describe the change"
```

## Deploy behavior

`render.yaml` runs `flask db upgrade && gunicorn app:app` on start.

The baseline migration (`a32baf980004`) is safe for **existing** databases:
if the `users` table already exists it creates nothing and only records the
revision — equivalent to `flask db stamp head`. Fresh databases get the full
schema. No manual step is needed either way.

## Rules

- Never edit an applied migration; add a new one.
- Review every autogenerated migration before committing (Alembic misses
  things like server defaults and some index changes).
- SQLite (dev) and Postgres (prod) don't behave identically — batch mode is
  enabled for ALTERs, but test schema changes against Postgres before deploy.
